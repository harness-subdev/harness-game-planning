# 공통 산출물 계약

각 프로젝트의 기존 기획 경로와 정본을 우선 사용한다. 없으면 `<project>/game-planning/`를 사용한다. 필요한 출력만 만들고 기존 파일·사용자 확정 결정·다른 작업자의 변경을 보존한다.

## 문서 모드와 원작 레퍼런스 보고서

작성·검수·HTML 단독 호출도 요청과 brief에서 목적을 식별한다. 제공되거나 프로젝트에 있는 사용자 피드백 정본과 용어·수정 목록은 전체 읽고 최신 확정 기준을 적용한다. 기존 보고서나 요약으로 대신하지 않으며 수정 후보를 새로 확인한 게임 사실로 바꾸지 않는다.

| 모드 | 정본과 산출물 | 담당 경로 |
| --- | --- | --- |
| 원작 레퍼런스 분석 | 지정된 보고서 또는 `01-research.md` 하나에 실제 게임의 개요·메커니즘·콘텐츠·설계 특징·참고자료를 설명한다. brief·용어·출처·검수는 별도 작업 기록으로 유지한다. | research가 작성·근거를 소유하고 필요한 원작 해석만 concept/systems/progression에 맡긴다. validation 내용 대조 후 html로 전달한다. |
| 신작 기획·제작 인계 | 아래 신작 파일 구성과 C/D/SYS/P/V, 기획·구현·검증 상태, 수락 조건을 사용한다. | research → concept → systems → progression → validation → html 중 요청 범위에 필요한 단계 |
| 원작 분석과 신작 적용을 함께 요청 | 원작 보고서와 적용·설계·제작·시험 문서를 구별한다. 원작 사실은 원작 정본을 참조하고 새 선택과 시험은 신작 계약으로 작성한다. | 먼저 원작 근거를 확보한 뒤 요청된 신작 단계에 입력으로 인계한다. |

원작 보고서를 신작 MVP·제작/QA·사람 시험 계획으로 확장하지 않는다. 원작 분석 지원 단계도 지정된 보고서의 담당 절을 작성하며 단계 파일을 채우기 위한 중복 정본을 만들지 않는다. 게임 화면·아트 제작, 런타임 구현, 사람 모집·시험 실행, 원격 배포는 요청된 경우에만 그 범위로 진행한다.

### 규칙별 정본

| 규칙 | 정본 |
| --- | --- |
| 원작 목차·분류·콘텐츠 상세, 모드별 파일·상태·인계 | 이 계약 |
| 장르별 전문어 조회·선택·의미 검수 | [V3 도메인 사전 조회와 보고서 적용](domain-dictionary.md). 메타데이터 우선·선택 범위 조회이며 프로젝트 피드백/확정 목록 전체 읽기와 구별한다. |
| 용어 정의·쉬운 문장·독자용 본문과 작업 기록 | [게임 기획 용어](game-terminology.md#용어-정본과-명칭-대조), [독자용 경계](game-terminology.md#독자용-문체와-작업-기록의-경계) |
| 실제 영상·UI 취득과 관찰·자료 설명·추론·미확인 | [research의 장면 취득](../../game-planning-research/SKILL.md#실제-플레이-장면과-ui-취득), [관찰과 해석](../../game-planning-research/SKILL.md#관찰과-해석의-경계) |
| 근거를 묻고 실제 원문을 고치는 내용 검수 | [근거 확인과 수정](deep-interview.md), 실행 담당은 [validation](../../game-planning-validation/SKILL.md) |
| 렌더러 선택·표시 데이터·실제 HTML 검수 | [HTML 스킬](../../front-game-planning-html/SKILL.md)과 그 portal-format 참조 |

각 단계는 해당 정본을 참조한다. 같은 절차를 다른 파일에 복사해 별도의 기본값으로 관리하지 않는다.

### 원작 보고서의 정형 목차

```text
1. 게임 개요
   1.1 기본 정보
   1.2 장르와 핵심 플레이
   1.3 세계관·이야기·주요 캐릭터
   1.4 전체 플레이 흐름 [Mermaid]
   1.5 스테이지 종류와 목표 및 확인된 진행 관계 [Mermaid]
   1.6 분석 범위
2. 게임 메커니즘
   2.1 아웃게임 - 준비와 진행 관리
       2.1.1 지도·지역·스테이지 선택/진입·해금
       2.1.2 미션·진행 목표/장기 목표·선택 목표
       2.1.3 장비/무기·보조 장비·필살기, 획득·장착 자리·조합 제한
       2.1.4 경제/재화·상점·가격·구매 조건
       2.1.5 캐릭터·난이도·협동 등 플레이 전 설정
       2.1.6 완료 평가·보상·진행 기록·저장
   2.2 인게임 - 조작과 실제 플레이
       2.2.1 장르별 플레이 방식과 하위 분기
       2.2.2 캐릭터 행동·모션
       2.2.3 전투/상호작용 규칙과 자원·상태
       2.2.4 UI·플레이어 피드백
       2.2.5 스테이지·보스 등 콘텐츠 상세
       2.2.6 난이도·실패·재시작·재도전
       2.2.7 히든 요소·특수 메커니즘
3. 핵심 설계 특징
4. 참고자료와 조사 범위
```

요청한 추가 깊이는 `2.1 → 2.1.1`과 `2.2 → 2.2.1`이며 위 목차가 그 결과다. 아웃게임 세부 시스템은 이 수준의 절 안에서 문단·표로 설명한다. 개별 스테이지처럼 독립 분석 대상이 있는 경우에만 필요한 하위 절을 구분한다.

- **개요:** 무엇을 조작하고 어떤 목표를 수행하는 게임인지 먼저 설명한다. 세계관·이야기·캐릭터는 실제 자료로 확인한 범위만 쓴다. 1.4는 준비 → 플레이 → 결과 → 다음 선택 등 확인된 반복을 그린다. 1.5는 전체 분류·목표와 확인된 선형/분기·선택·해금 관계를 상세 사례보다 먼저 보여 준다. 화살표의 뜻과 그림의 범위를 밝히고, 미확인 진행은 분류도와 구별한다. 1.6은 본편/확장, 전체 구조를 소개한 범위와 상세 분석 대상을 구별한다.
- **아웃게임/인게임:** 장비의 획득·가격·장착은 2.1, 전투 중 발사·효과·사용 조건은 2.2다. 장기 목표·계약은 2.1, 현장 승리·출구 도착 등의 완료 조건은 2.2다. 완료 후 평가·보상·진행 기록은 2.1.6에 둔다. 같은 설명을 복사하지 않고 관련 절로 연결한다.
- **인게임 상세:** 실제 존재하는 이동·점프·대시·조준·사격·패링 등 행동과 모션, 체력·피격·피해·무적·카드·기술·사망·협동 구조, 상태 표시·공격 예고·색·모션·효과음·결과를 확인한다. 공략 변경과 같은 공략의 조작 타이밍·착지 조정을 구별한다. 미확인 HP·스토리·히든 조건·정밀 프레임을 목차 때문에 채우지 않는다.
- **설계 특징:** 앞서 설명한 시스템 간 연결을 실제 근거로 종합한다. 원작의 행동·선택·결과를 설명하고 다른 게임에 적용할 새 정책이나 QA 과제를 끼워 넣지 않는다.
- **참고자료:** 공식 자료 소개에는 수집한 공식 자료의 제목과 직접 링크를 둔다. 위키·가이드·리뷰·개인 영상은 공식 자료와 구별해 해당 설명 옆의 직접 원자료로 연결한다. 실제 조사일·관찰 조건·중요 미확인과 규칙에 영향을 주는 게임 패치 차이는 유지한다.

상위 구조와 분류 원칙은 유지하되 게임의 장르·실제 시스템에 맞춰 이름과 하위 제목을 구체화한다. 없는 보스·장비·미션·전투는 제외 이유를 작업 기록에 남기고 독자용 목차에서 의미 없는 빈 장을 제거한다. 남은 하위 절은 같은 깊이로 순서대로 번호를 붙이고 표준 항목과의 대응은 작업 기록에 남긴다. 스테이지가 없는 게임은 실제 플레이 단위의 종류·목표·진행으로 바꾼다.

Cuphead 회귀 예시는 **캐그니 카네이션·그림 매치스틱·글럼스톤·힐다 베르그의 네 보스전과 숲속 소동·위험한 부두의 두 횡스크롤 액션 스테이지**다. 여섯 보스로 세거나 사례 순서를 실제 필수 진행 순서로 그리지 않는다. 이 대상과 수량은 다른 게임의 기본값이 아니다.

### 콘텐츠 상세 양식

- **보스전:** 스테이지명·종류·목표 → 배경·스토리·보스 역할 → 전투 공간 → 체력·전환 조건(확인한 범위만) → 단계별 패턴 → 예고·공격·회복 모션 → 대응·공략 조건 → 완료 보상.
- **횡스크롤 액션 등:** 스테이지명·목표 → 배경·스토리 → 구간·이동 경로 → 적·장애물 → 수집·우회 선택 → 실패 위험·완료 조건 → 보상.
- **퍼즐·탐색·비전투:** 해당 장르의 대상·상호작용·목표에 맞게 위 상세 양식을 바꾼다. 예를 들어 퍼즐은 대상 배치·조작·변화 조건·해결 목표, 탐색은 이동 경로·발견·상호작용·진행 관계를 다룬다. 존재하지 않는 전투 단계·적 체력·승패·보상을 추가하지 않는다.

## 원본과 파생물

### 원작 보고서

- 독자용 정본은 지정된 보고서 또는 `01-research.md` 하나다. 개요부터 참고자료까지 그 문서에서 이해할 수 있게 작성한다.
- 사용자 범위는 기존 brief, 명칭은 기존 사전 또는 `00-glossary.md`, 원자료는 기존 출처 기록 또는 `sources.json`에 관리한다.
- 내부 질문·수정·검수·취득 실패·제외 사유는 기존 `05-validation.md`, `evidence/`, `workflow.json` 등 별도 작업 기록에 남긴다. 표시 범위는 위 용어 정본을 따른다.
- 표시 데이터와 HTML은 선택한 프로젝트 렌더러의 형식을 사용한다. 기본 portal version 1의 형식과 기능을 원작 보고서의 지원으로 간주하지 않는다.

외부 CSV/JSON/코드가 특정 수치의 정본이면 경로와 소유권을 brief에 기록해 참조한다. 같은 수치를 문서에서 독립 관리하지 않는다. 사용자 요구는 brief에 보존하며 validation은 현재 반영 위치·제외 이유·남은 충돌을 대조한다.

두 모드 모두 문서 변경 → 표시 데이터 갱신 → HTML 생성 순서다. 필요한 기능을 지원하는 기존 프로젝트 렌더러를 재사용한다. 현재 빌더가 Markdown을 자동 의미 해석하거나 동기화하는 기능은 없다. 생성된 HTML의 내용만 따로 고쳐 원문과 다르게 관리하지 않는다.

## 근거 추적

원작은 `출처 S → 관찰/자료 설명 R → 보고서의 규칙·사례·설계 특징`으로 추적한다. 내부 ID는 기록에 사용하고 독자에게 대상 이름과 직접 원자료 링크를 제공한다.

신작의 중요한 결정은 `출처 S → 관찰 R → 결정 D → 명세 SYS/P → 검증 V`로 연결한다. C는 컨셉 가설이다. 독자적인 아이디어는 사용자 요구 또는 새 가설로 기록하며 외부 출처를 만들어 붙이지 않는다. 안정적인 ID는 의미를 유지하고 삭제된 ID를 다른 내용에 재사용하지 않는다. HTML 기획 허브에는 필요한 ID를 소문자 앵커로 매핑할 수 있다. 문장마다 ID를 강제하지 않는다.

### sources.json

기존 기록을 우선한다. 다음은 특정 게임 사실을 담지 않은 형식 예시다.

```json
{
  "schema_version": 1,
  "sources": [
    {
      "id": "S-01",
      "title": "사용자 분석 범위",
      "locator": "00-brief.md",
      "accessed_at": "2026-10-13",
      "published_at": null,
      "kind": "user",
      "reliability_note": "요청 범위이며 게임 규칙의 확인 자료는 아님"
    }
  ],
  "findings": [
    {
      "id": "R-01",
      "source_ids": ["S-01"],
      "location": "분석 범위",
      "observation": "사용자가 본편과 확장을 구별해 소개하도록 요청함",
      "interpretation": "보고서의 범위에서 두 대상을 구별",
      "confidence": "supported"
    }
  ],
  "conflicts": []
}
```

`kind`: user, official, observed, secondary. `confidence`: observed, supported, hypothesis, unknown. 관찰의 의미·수치 측정·취득 기록은 research 정본을 따른다. 실제 조사일을 기록하고 게시일을 모르면 null로 둔다. 접근 실패는 실패 사실만 기록하며 원문이나 화면을 확인한 것으로 쓰지 않는다. 신작의 `application`은 실제 적용 후보가 있을 때 추가한다. 원작 기록에 설계 선택을 채우기 위한 필드가 아니다.

충돌 기록에는 서로 다른 주장·source_ids·영향받는 보고서 항목 또는 신작 결정·해결 근거·남은 미확인을 남긴다. 출처 날짜·조건·사용자 결정을 비교하며 최신이라는 이유만으로 게임 사실의 승자를 자동 선정하지 않는다.

## 문서 단계 상태

`pending`, `running`, `done`, `stale`, `blocked`는 문서 작업 상태다. 해당 산출물을 실제 대조했으면 done이며 사용자 승인·구현 완료·게임의 재미 입증과 다르다. 제한으로 실행하지 못한 검수는 작업 기록에 남기고 완료 범위를 한정한다.

## 신작의 기획·구현·검증 상태

- **기획 항목:** proposed, confirmed, deferred. confirmed는 명시된 사용자 결정 또는 기존 승인 자료가 있을 때 사용한다.
- **구현:** not_started, prototype, implemented, unknown. 기획 작성만으로 implemented로 올리지 않는다.
- **검증 근거:** not_run, illustrative, calculated, observed. 도식은 illustrative, 모델 결과는 calculated, 실제 플레이 기록은 observed다.

각 V에는 검증 방법, 실제 플레이 주체 human 또는 agent(플레이할 때), 조건·버전, 원자료 위치, 판정 가능한 주장 범위를 기록한다. 에이전트 문서 검토·모델 계산·직접 플레이·사람 플레이 증거 분석을 구별한다. 실제 에이전트 플레이도 observed일 수 있으므로 이 상태만으로 인간 경험을 판정하지 않는다. 실제 사람이 참여하지 않은 반응을 생성해 재미 검증으로 쓰지 않는다. 기준 충족 여부는 위 상태와 별도로 기록한다.

두 모드에서 숫자 0은 관측값 0이다. 모르는 값은 null/미정, 측정하지 않은 값은 미측정이다. 목표·가정·계산·실측을 구별하고 분모·단위·조건·적용 범위를 붙인다. 계산 난도와 실제 성공률, 모델 점수와 사람 재미를 합치지 않는다.

## workflow.json

요청 범위에 실제 필요한 단계만 기록한다. 다음은 원작 분석의 예시다. 지원 단계가 별도 작업을 맡았을 때만 그 단계와 담당 출력을 추가한다.

```json
{
  "schema_version": 1,
  "project_id": "reference-game",
  "updated_at": "2026-10-13",
  "stages": {
    "research": {
      "status": "pending",
      "input_sha256": {},
      "outputs": [],
      "notes": []
    },
    "validation": {
      "status": "pending",
      "input_sha256": {},
      "outputs": [],
      "notes": []
    },
    "html": {
      "status": "pending",
      "input_sha256": {},
      "outputs": [],
      "notes": []
    }
  },
  "decisions": [],
  "next_action": "대상 게임·분석 범위·기존 자료 확인"
}
```

신작 전체 기획에서는 research/concept/systems/progression/validation/html을 같은 단계 객체 형식으로 기록한다. 단독 호출이면 요청된 단계만 사용한다. 모드는 brief에서 관리하며 없는 문서를 만들기 위해 모든 단계를 복사하지 않는다. 실제로 수행하지 않은 내부 문답·재검토 횟수를 기록하지 않는다.

입력 해시의 키는 프로젝트 기획 경로 기준 상대 경로, 값은 실제 최종 바이트의 SHA-256이다. `workflow.json`은 자기 입력 해시에서 제외해 완료 기록 때문에 스스로 stale이 되는 순환을 막는다. 입력이자 출력인 파일은 저장을 마친 최종 해시를 기록한다. research가 brief를 만드는 첫 실행도 저장 후 해시를 잡는다. HTML은 표시한 선행 상태를 `input_states`에 기록해 재개 때 비교하며 자신의 running/done은 넣지 않는다. 예: `{"research":"done","validation":"done"}`.

결정 항목은 기존 `id`, `question`, `choice`, `basis_ids`, `status`(proposed/confirmed/deferred/superseded), `owner`(user/agent/source), `affected_ids`를 사용한다. 규칙에 영향을 주는 변경은 해당 정본에도 반영하고 이전 결정은 superseded로 보존한다. 원작에는 실제 분석 범위·해석 결정만 기록한다.

### 완료 인계

각 단계는 출력 경로·담당 위치, 소비한 입력·용어 정본과 V3 조회 선택(사전 경로/해시·node ID/key·mode/scope·주 범위/별도 참조·본문 사용 위치), 실제 확인 근거, 수정 위치, 남은 가정·충돌·제외 사유, 실행/미실행 검사와 다음 담당을 반환한다. 원작 인계에는 보고서 위치와 장면·출처 대응을, 신작 인계에는 결정·SYS/P/V와 상태·수락 조건을 사용한다. 내용 검수 담당은 validation, 근거 보완은 research, 표시 검수는 html이다. 총괄만 workflow.json을 갱신하며 단독 실행에서는 해당 실행의 총괄 역할이 맡는다.

### 구현 요청 시 인계

신작의 실제 구현을 요청받으면 다음을 기존 SYS/P/V 정본에서 인계한다.

| 항목 | 포함 내용 |
| --- | --- |
| 목적·범위 | C/V 질문, 시험할 경험, 필요한 최소 화면·입력·피드백·콘텐츠·구현과 제외 범위 |
| 정본·결정 | SYS/P/D, 경로·버전, 확정/제안/미정 조건과 사용자 요구 |
| 수락 조건 | 정상·경계·실패의 초기 조건 → 입력·행동 → 기대 상태·피드백·복구. 해당 사례가 없으면 이유 |
| 검증·증거 | V, 기능 검사/모델/플레이 방법과 주체, 실행 조건·원자료·판정 범위 |
| 후속 소유권 | 실패·미정 조건을 고칠 기획/디자인/구현 담당과 변경 영향 |

사용자가 선택한 현재 구현 절차와 이미 제공한 승인을 따른다. 기획 정본을 복제한 GDD/epics/decision-log나 별도 런타임·PM 체계를 추가하지 않는다. 기획만 요청됐으면 제작을 시작하지 않는다. 준비되지 않은 시험은 not_run으로 남긴다. 기능 수락과 인간 경험 판정은 별개이며 실제 제작·시험 결과가 들어오면 validation으로 분석한 뒤 담당 정본을 수정한다.

### 재개와 변경 영향

| 변경 | 원작 보고서 | 신작 기획 |
| --- | --- | --- |
| 대상·범위·사용자 요구 | brief·research 및 영향을 받은 validation/html | research와 관련 concept/systems/progression, validation/html |
| 조사 근거·규칙·해석 | 해당 원문·그림/장면·validation/html | 근거를 참조하는 기획 단계와 그 하위 출력 |
| 컨셉·루프·성공/실패 정책 | 해당 없음. 원작 규칙 정정은 위 행 | systems/progression/validation/html |
| 시스템·수치·진행 설계 | 해당 없음. 원작 규칙 정정은 위 행 | 관련 SYS/P와 validation/html |
| 실행 검증 결과 | 해당 원작 주장과 조건·미확인, validation/html | 실패 가설 소유 단계와 그 하위 출력 |
| 용어 정의·개념 경계 | 해당 개념을 쓰는 원문·validation/html | 해당 개념을 쓰는 정본·validation/html |
| 표기·오탈자·표현만 | 의미가 같은지 확인 후 해당 원문/html | 의미가 같은지 확인 후 해당 원문/html |
| HTML 색·간격만 | html | html |

재개할 때 done의 실제 입력 해시·출력 존재와 HTML의 선행 `input_states`를 확인한다. 해시가 없으면 기존 완료를 확인하지 않은 상태로 검토한다. 바뀐 입력을 참조하는 부분에 stale과 이유를 기록하고 영향이 불명확하면 관련 부분을 확인한다. 새 근거 하나 때문에 모든 조사를 기계적으로 다시 실행하지 않는다.

해시 생성·의미/원자료 대조·상태 기록은 실행 에이전트의 작업이다. 표시 데이터 형식 검사와 별개이며 자동 스케줄러·동기화가 구현됐다고 설명하지 않는다.
