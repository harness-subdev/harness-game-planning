# 게임 기획 오케스트레이터

기획 자료를 모으는 데서 끝내지 않고, 근거와 선택 이유를 추적할 수 있는 게임 기획 문서와 로컬 HTML까지 만든다. 기본 대상은 개발 예정·개발 중인 게임이다. 레퍼런스 분석은 주로 research에서 하며 레퍼런스 자체의 명세화는 요청된 경우에만 수행한다.

systems는 규칙 명세, progression은 학습·난도·성장·회복·콘텐츠 진행 설계다. 둘은 Game Design의 일부이며 실제 게임을 실행하거나 플레이를 진행하는 단계가 아니다. 게임 화면·아트·시청각 자산 제작, 런타임 구현, 원격 배포는 별도 요청 범위다.

## 시작

1. 사용자가 준 게임 아이디어·파일·URL·기존 코드/기획을 읽는다. 프로젝트의 기존 용어와 확정 결정을 보존한다.
2. [공통 산출물 계약](references/artifact-contract.md)을 읽는다. 아래 자식 스킬은 필요한 단계에서만 읽는다. 다른 프로젝트의 게임 규칙·스테이지 수를 기본값으로 가져오지 않는다.
3. 기존 `game-planning/workflow.json`이 있으면 진행 상태, 출력 존재, 실제 입력 해시를 확인해 재개한다. 경로를 사용자가 정했으면 따른다.
4. 신규 프로젝트라면 brief에 알려진 정보·미지수·가정을 적는다. 사용자 답이 결과를 크게 바꾸는 질문만 묶어서 요청하고 독립적인 자료 검토를 계속한다. 작은 선택은 근거와 함께 제안으로 결정한다.
5. 사용자가 요청한 범위를 기록한다. ‘분석만’, ‘컨셉만’이면 거기서 마친다. ‘기획서까지/전체’면 HTML 열람본까지 진행한다. 이미 제공된 승인을 다시 요구하는 단계 관문을 만들지 않는다.

## 단계 라우팅

| 단계 | 스킬 파일 | 완료 산출물 |
| --- | --- | --- |
| research | [game-planning-research](../game-planning-research/SKILL.md) | brief, sources, 조사·비교·선택 근거 |
| concept | [game-planning-concept](../game-planning-concept/SKILL.md) | 핵심 재미 가설, 플레이 루프, MVP |
| systems | [game-planning-systems](../game-planning-systems/SKILL.md) | 규칙, 상태, 콘텐츠, 수치 명세 |
| progression | [game-planning-progression](../game-planning-progression/SKILL.md) | 학습·세션·성장/콘텐츠 진행 |
| validation | [game-planning-validation](../game-planning-validation/SKILL.md) | 모순 검수, 검증 계획, 실제 근거와 미실행 목록 |
| html | [front-game-planning-html](../front-game-planning-html/SKILL.md) | portal.json, 빌드된 index.html, 열람 검수 결과 |

경로는 스킬 설치 루트의 형제 폴더 기준이다. 파일이 누락되면 설치된 스킬 목록에서 정확한 이름을 찾는다. 찾지 못한 필수 단계는 누락을 명시하고 같은 계약으로 일반 작업을 계속할 수 있으나 해당 스킬을 실행했다고 주장하지 않는다.

## 순서와 분담

`research → concept → systems → progression → validation → html`

이는 기획 문서의 의존 순서이며 실제 게임 제작·재미 검증이 끝나는 순서가 아니다. 단계를 시작할 때 정본 입력과 완료 기준을 전달하고, 결과를 확인한 뒤 다음 단계로 이동한다. 조사 결과가 기획에 반영되지 않으면 자료 목록을 늘리기보다 필요한 설계 질문으로 돌아간다.

실제 제작의 반복은 `기획 → 검증 질문/계획 → 필요한 디자인·구현 → 플레이테스트 → 기획/디자인/구현 수정`이다. 핵심 위험이 드러나면 전체 콘텐츠 작성 전에도 validation으로 질문과 계획을 정리한다. 손맛·분위기 등 확인할 경험을 플레이 가능한 수준으로 준비해야 그 경험을 시험할 수 있다. validation은 구현 전 문서 검수·테스트 설계와 실행 증거가 들어온 뒤의 분석에 다시 사용한다. HTML은 현재 기획과 미검증 상태를 보여 주는 열람본이다.

구현 요청이 있으면 [공통 계약의 구현 인계](references/artifact-contract.md#구현-요청-시-인계)에 따라 SYS/V와 수락 조건을 현재 사용자 구현 워크플로로 넘긴다. 현재 정책은 `brainstorming → writing-plans → implement 또는 subagent-driven-development → verification-before-completion`이며 기존 승인을 보존한다. GSD는 프로젝트 관리에만 사용하고 GSD-native discuss/plan/execute는 명시적으로 요청된 경우에만 사용한다. BMAD 런타임·별도 PM/스프린트 체계·중복 GDD/epics/decision-log 정본을 추가하지 않는다.

독립적인 레퍼런스 조사, 기술 제약 확인, 완성된 기획의 검수는 에이전트로 병렬화할 수 있다. 같은 문서의 최종 작성자는 한 명만 지정한다. 선행 결정에 의존하는 컨셉/시스템/진행을 동시에 확정하지 않는다. 에이전트 도구가 없으면 동일한 단계들을 직접 수행한다. 이 스킬은 대화 중 실행하는 절차이며 백그라운드 스케줄러가 아니다.

하위 작업 인계에 반드시 포함할 것:
- 목적과 범위, 확정된 사용자 결정.
- 읽을 입력 경로·출처 ID, 작성 권한이 있는 출력 경로.
- 이 단계의 완료 기준과 미지수 처리 기준.
- 공통 계약 경로. 다른 작업자의 변경을 덮어쓰지 않을 것.

각 단계의 출력과 인계 요약을 확인한 후 총괄만 workflow.json을 갱신한다. 파일 경로/존재, 핵심 ID 참조, 관찰과 추론의 구분을 확인한다. 검증 근거는 방법·플레이 주체·조건·원자료·판정 가능한 주장 범위를 함께 확인한다. 검수 전에는 done을 기록하지 않는다. 답변 대기 때문에 특정 분기가 막혀도 독립적인 문서/조사는 진행한다.

## 결정과 불확실성

기획 항목의 confirmed, 구현 완료, 플레이 검증 완료는 서로 다르다. 제안을 자동 승인으로 바꾸지 않는다. 기존 자료가 충돌하면 출처·날짜·실제 동작·사용자 결정을 비교하고 결론 및 남은 불확실성을 기록한다. 접근할 수 없는 URL이나 아직 실행하지 않은 테스트를 근거로 삼지 않는다.

핵심 가설이 미검증이어도 초안 기획서와 HTML은 만들 수 있다. 상태와 검증 계획을 읽는 사람이 볼 수 있게 표시한다. 새 게임 정보가 거의 없으면 중요한 질문을 남기고 조사 프레임과 후보안을 준비한다. 특정 게임을 임의로 확정해서 완성 기획서처럼 내지 않는다.

## 재개와 반복

공통 계약의 변경 영향표에 따라 실행 에이전트가 해시를 비교하고 stale을 기록한다. 이는 지침에 따른 작업이며 SKILL.md나 HTML 빌더가 자동 강제·동기화하는 기능이 아니다. 예를 들어 조작 규칙 변경은 시스템·진행·검증·HTML에 영향을 주지만 CSS 간격 수정은 HTML에만 영향을 준다. 기존 output이 있다는 이유로 완료를 가정하지 않는다.

- `계속`: done의 입력 해시와 출력 존재를 확인한 뒤 첫 pending/stale부터 재개한다.
- `규칙/컨셉 수정`: 해당 정본을 수정하고 참조하는 하위 단계만 다시 검토한다.
- `다른 게임`: 새 프로젝트별 출력 경로와 brief를 사용한다. 이전 게임의 수치·관측을 넘기지 않는다.
- `HTML만 재생성`: 정본 및 validation의 현재 상태를 읽어 표시 데이터를 재생성한다. stale/미검증 상태를 지우지 않는다.

반복은 발견한 문제를 소유한 단계로 돌아간다. 새로운 근거 없이 같은 점수를 반복 계산하지 않는다. 수정이 사용자 제약/핵심 선택을 바꿔야 하면 그 결정만 물으며 다른 일을 계속한다.

## 최종 전달 기준

1. 요청 범위의 문서가 있고 선택한 규칙이 서로 모순되지 않는다. 미결정 항목은 눈에 띄게 남긴다.
2. 주요 결정의 근거·명세·검증 연결을 따라갈 수 있다. 검색 결과에 제목/직접 링크/접근일이 있다.
3. 실제로 실행한 검수와 계획만 세운 검증을 분리한다. 사람의 재미·성공률을 추정 점수나 에이전트 플레이로 입증했다고 쓰지 않는다. 실제 에이전트 플레이도 observed일 수 있으므로 근거 배지만으로 인간 경험을 판정하지 않는다.
4. HTML의 원문 반영, 탐색, 링크, 좁은 화면, 빈 상태를 확인한다. 브라우저는 사용자의 연결 Chrome 정책을 따른다. 접근이 불가능하면 그 검수만 미실행으로 표시한다.
5. workflow.json에 입력 해시·산출물·다음 행동을 남긴다. 최종 메시지에는 문서/HTML 경로, 핵심 결정, 남은 질문·미실행 검증을 짧게 제공한다.

사용 예: `$game-planning-workflow 세로 화면 모바일 퍼즐을 기획해줘. 한 손 조작, 짧은 세션, 2인 개발팀이며 제공한 자료와 공개 레퍼런스를 조사해 기획서와 로컬 HTML까지 만들어줘.` 예시 조건은 새 프로젝트의 기본값이 아니다.
