# 게임 기획 오케스트레이터

요청한 게임 분석이나 기획을 근거가 있는 문서와 로컬 열람본으로 완성한다. 원작 분석은 실제 게임을 설명하는 보고서이고, 신작 기획은 만들 게임의 선택과 규칙을 정하는 문서다. 요청에서 목적을 식별하고 아래 해당 경로를 사용한다.

## 시작과 정본

1. 사용자 자료·기존 기획·코드와 확정 결정을 읽고 요청 범위·출력 경로를 확인한다. [문서 모드와 산출물 계약](references/artifact-contract.md#문서-모드와-원작-레퍼런스-보고서)을 적용한다. 제공되거나 프로젝트에 있는 피드백 정본·용어/수정 목록은 길어도 전체 읽고 최신 확정 기준을 우선한다. 수정 예시를 새 관찰 사실로 바꾸지 않는다.
2. 기존 brief·용어 정본·출처 기록·보고서·렌더러를 확인한다. [V3 도메인 사전 조회와 보고서 적용](references/domain-dictionary.md)에 따라 메타데이터부터 장르·하위 유형을 대응시켜 이름 정의와 전문어를 구별하고 필요한 범위만 조회한다. 앞 항목의 전체 읽기는 프로젝트 피드백·확정 용어 목록에 적용하며 V3 본문 전체 읽기로 확대하지 않는다. [용어 정본과 명칭 대조](references/game-terminology.md#용어-정본과-명칭-대조)에 따라 본문 전에 필요한 명칭을 정한다. 특정 프로젝트의 절대 경로·게임 규칙·사례 수를 새 프로젝트의 기본값으로 가져오지 않는다.
3. 기존 `workflow.json`이 있으면 요청 모드의 단계, 실제 입력 해시와 출력 존재를 확인해 재개한다. 총괄만 상태를 갱신한다. 새 작업 기록은 기존 기획 경로를 사용하며 중복 보고서·결정 정본을 만들지 않는다.
4. ‘분석만’, ‘컨셉만’, ‘HTML만’ 등 지정 범위를 따른다. 전체 보고서·기획서와 열람본을 요청받으면 필요한 작성·수정·검수·HTML까지 진행한다. 이미 제공된 승인을 다시 요구하는 단계 관문을 만들지 않는다. 자료로 확인할 수 없는 사실은 미확인, 새로운 설계 선택은 제안으로 기록하고 독립적으로 가능한 작업을 계속한다.

## 보고서의 기본 언어 검수

원작·신작의 작성·수정은 [프로젝트 용어 + STE-KO 검수](references/report-language.md)를 기본 실행한다. 작성 전 기존 프로젝트 사전과 선택 V3 정의를 확인하고 STE-KO `문서` 표면으로 작성한다. 작성 후 자동 탐지 → 제목·본문·표·캡션의 용어 의미 및 수동 문체 대조 → 실제 원문 수정·재검사 → 기존 `05-validation.md`/`workflow.json` 기록 → 최종 실행기 순으로 닫는다. `--lint-only` 성공만으로 완료하지 않는다. 전체 요청의 validation 단계는 최종 실행기를 각 독자용 문서에 호출하며 입력·검사 누락/실패·stale 기록이면 해당 검수를 완료로 올리지 않는다. HTML만 요청되면 선행 검수의 현재성·미실행 범위를 확인하고 새 원문 작성까지 확장하지 않는다.

필요한 단계에서만 담당 스킬을 읽는다. 스킬이 누락되면 설치 목록에서 정확한 이름을 찾고, 찾지 못한 기능은 가능한 일반 작업으로 이어가되 그 스킬을 실행했다고 보고하지 않는다. 같은 문서의 최종 작성자와 용어 사전 담당은 각각 한 명을 정한다. 독립적인 조사는 병렬로 진행할 수 있고, 앞 결정에 의존하는 설계는 그 결과를 받은 뒤 작성한다.

## 원작 레퍼런스 보고서 경로

전체 구조 소개와 상세 분석 대상을 구별해 하나의 독자용 보고서를 만든다. [정형 목차](references/artifact-contract.md#원작-보고서의-정형-목차)와 [장르별 콘텐츠 상세](references/artifact-contract.md#콘텐츠-상세-양식)가 작성 기준이다. 필요한 중간 작업을 다음과 같이 연결한다.

| 순서 | 담당 | 입력 → 수행 → 출력·다음 단계 |
| --- | --- | --- |
| 1. 범위·명칭 정리 | research | 사용자 자료·최신 피드백·V3 메타데이터 → 본편/확장·전체 소개/상세 대상·장르 노드·주 범위/별도 참조·명칭 확인 → brief·선택 용어 정본·조사 질문 |
| 2. 조사 항목과 화면 대응 | research | 질문·정형 목차 → 각 설명에 필요한 규칙·자료·실제 UI·전후 장면 대응 → 조사 목록·출처 탐색 |
| 3. 원자료·영상 탐색 | research | 조사 목록 → 공식 자료 우선 웹 검색, 부족한 실제 플레이는 공개 원저자 영상 탐색 → 직접 URL·원저자·조건·관찰할 구간 |
| 4. 실제 관찰·캡처 | research | 원영상·구간 → [실제 플레이 장면과 UI 취득](../game-planning-research/SKILL.md#실제-플레이-장면과-ui-취득) → 저장 픽셀까지 대조한 캡처·설명·출처 기록 또는 근거 상태를 밝힌 문서 수준 설명 |
| 5. 개요·전체 흐름 작성 | research, 필요한 경험 해석은 concept | 확인한 자료·규칙 → 기본 정보·세계관·핵심 플레이·분석 범위 작성 → 개요 초안·확인된 반복과 진행 관계 |
| 6. 흐름 그림 작성 | mermaid-diagrams, 진행 해석은 progression | 확인된 반복·종류·목표·연결 → 분류/선형/분기/해금의 뜻과 범위를 표시 → 1.4·1.5 Mermaid와 짧은 설명 |
| 7. 메커니즘·콘텐츠 작성 | research, 규칙 해석은 systems | 자료·관찰 기록·확보한 캡처 → 아웃게임/인게임 분류와 장르별 상세 작성, 설명 옆 출처·근거 상태와 확보한 장면 배치 → 2절. 진행·재도전 관계는 progression에 필요한 부분만 인계 |
| 8. 설계 특징 종합 | research, 필요한 해석은 concept/systems/progression | 1·2절의 실제 근거 → 시스템 사이 행동·선택·결과 연결 → 3절, 직접 원자료·조사 조건·중요 미확인 → 4절 |
| 9. 내용·근거·용어·문체 확인과 수정 | validation → 문제 소유 단계 | 보고서·용어·원자료·관찰 기록·확보한 캡처 → 목차·분류·주장·선택 용어의 정의/개념 경계·문서 수준 설명·장면 대응 대조 → 실제 원문 수정·영향받은 부분 재확인·기본 언어 검수 실행과 현재 기록 확인. 부족한 근거는 research로, 잘못된 해석은 담당 작성자로 반환 |
| 10. HTML 표시 방식 선택·생성 | front-game-planning-html | 수정된 보고서·그림·장면 기록 → 지원 가능한 기존 렌더러 선택 또는 요청된 HTML 범위의 최소 보완 → 표시 데이터·HTML. 필수 근거가 사라지는 형식으로 축소하지 않음 |
| 11. 실제 표시 검수·전달 | front-game-planning-html | 문서·표시 데이터·HTML → 연결 Chrome에서 정상/좁은 화면과 로컬 근거의 열람 대조 → 표시 문제 수정, 내용 문제는 validation/작성 단계로 반환 → 보고서·HTML·별도 작업 기록 |

concept/systems/progression의 원작 분석 경로는 위 보고서의 담당 위치에 작성한다. 신작의 컨셉·SYS/P·QA·시험 문서를 채우는 작업으로 바꾸지 않는다. 신작 적용도 요청됐으면 [모드별 산출물](references/artifact-contract.md#문서-모드와-원작-레퍼런스-보고서)에 따라 별도 제안 문서로 연결한다.

## 신작 기획 경로

`research → concept → systems → progression → validation → html` 순으로 필요한 문서를 작성한다. 각 작성 단계는 선택한 V3 전문어의 정의·구별 기준·의미 차이·예문·ref를 확인해 프로젝트 명칭을 사용하고, validation은 실제 문장의 의미와 작품 근거/신작 정의를 대조한다. research의 원작 근거를 concept에 넘겨 경험·선택·MVP를 정하고, systems는 그 선택의 규칙·상태·수치·수락 조건을, progression은 도입·학습·회복·콘텐츠 연결을 작성한다. validation은 현재 정본의 모순과 가설별 검증 방법·필요한 준비·실행 증거를 대조한다. HTML에는 [신작 전용 상태](references/artifact-contract.md#신작의-기획구현검증-상태)를 표시한다.

핵심 위험이 먼저 드러나면 해당 정본을 validation에 넘겨 검증 질문과 필요한 준비를 정하고 담당 단계로 돌아간다. 구현 요청이 있으면 [구현 요청 시 인계](references/artifact-contract.md#구현-요청-시-인계)의 SYS/P/V·수락 조건을 사용자의 현재 구현 절차로 전달한다. 실제 제작은 필요한 디자인·구현 → 플레이테스트 → 기획/구현 수정으로 이어지며 문서 작성만으로 재미를 검증한 것으로 처리하지 않는다.

## 인계와 재개

하위 작업에는 목적·모드·확정 결정, 읽을 입력과 작성할 출력, 보고서 담당 위치 또는 신작 ID, 용어 정본과 V3 사전 경로/해시·선택 node ID/key·조회 mode/scope·별도 참조 및 본문 사용 위치, 필요한 근거와 현재 부족한 범위를 전달한다. [완료 인계](references/artifact-contract.md#완료-인계)에 따라 실제 파일·출처·수정 위치·남은 한계를 회수한다. 다른 작업자의 변경을 덮어쓰지 않는다.

[변경 영향](references/artifact-contract.md#재개와-변경-영향)에 따라 바뀐 입력을 참조하는 단계만 재검토한다. 문서 → 표시 데이터 → HTML 순으로 갱신하고 실제 확인 범위를 작업 기록에 남긴다. 해시·상태 갱신은 실행 에이전트의 작업이며 빌더의 자동 동기화 기능이 아니다.

- `계속`: 요청 모드의 첫 pending/stale부터 재개한다.
- `규칙/컨셉 수정`: 해당 정본과 영향을 받은 부분을 갱신한다.
- `다른 게임`: 새 프로젝트의 범위·명칭·자료를 사용한다.
- `HTML만 재생성`: 현재 원문·검수 결과·상태를 읽고 표시를 갱신한다. 새 내용 인터뷰를 시작하지 않는다.

## 최종 전달

요청 범위의 문서·그림·근거·HTML과 실제 실행한 검수 결과를 전달한다. 문체와 기록의 표시 범위는 [독자용 문체와 작업 기록의 경계](references/game-terminology.md#독자용-문체와-작업-기록의-경계), 화면 검수는 HTML 스킬의 기준을 따른다. 미실행 검사를 통과로 보고하지 않는다. 최종 메시지에는 문서/HTML 경로, 핵심 내용, 남은 한계만 짧게 적고 내부 검수 기록을 독자용 보고서에 투영하지 않는다.

사용 예: `$game-planning-workflow 제공한 게임의 규칙과 진행을 조사해 원작 레퍼런스 보고서와 로컬 HTML로 만들어줘.` 신작 기획 요청에는 해당 프로젝트의 경험·플랫폼·제약을 입력으로 사용한다.
