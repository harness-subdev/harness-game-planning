# 게임 기획 검수와 검증

요청한 보고서의 설명·근거를 대조하거나 신작의 가설과 실제 시험 결과를 검토한다. 문서 검수, 공개 영상 관찰, 게임 기능 확인, 사람의 경험 검증을 구별한다.

## 기본 용어·문체 검수

[프로젝트 용어 + STE-KO 보고서 검수](../game-planning-workflow/references/report-language.md)를 단독 호출에도 적용한다. 작성 전 프로젝트 사전의 실제 사용 항목·명칭 상태·정의·구별을 확인하고 선택 V3와 STE-KO 문서 표면을 적용한다. 작성 후 자동 검사와 실제 문장의 의미·수동 문체 대조를 수행하고 원문 수정·재검사로 닫는다. 총괄은 기존 workflow/05-validation에 범위·해시·판정을 기록하고 최종 실행기를 호출한다. 하위 작업은 실제 실행 결과와 미실행을 총괄에게 인계한다. 단독 실행자는 총괄 역할을 맡는다. 자동 탐지만으로 의미 준수나 최종 완료를 주장하지 않는다.


## 진입과 작업 기록

- [문서 모드와 산출물 계약](../game-planning-workflow/references/artifact-contract.md#문서-모드와-원작-레퍼런스-보고서)을 읽고 원작 분석·신작 기획·명시적으로 요청한 시험의 범위를 식별한다. 제공된 사용자 피드백 정본과 용어·수정 목록은 전체 읽고 최신 확정 기준을 적용한다.
- [용어 정본과 명칭 대조](../game-planning-workflow/references/game-terminology.md#용어-정본과-명칭-대조) 및 [독자용 문체와 작업 기록의 경계](../game-planning-workflow/references/game-terminology.md#독자용-문체와-작업-기록의-경계)를 보고서 제목·본문·표·캡션·링크 이름·부록과 대조한다.
- 원작 분석의 입력은 지정 보고서·사전·출처·캡처·기존 작업 기록이다. 검수 결과·내용 질문·수정 위치·제외 사유는 별도 작업 기록에 저장한다. 공통 계약에서 정한 기록 경로가 있으면 재사용한다.
- 신작 기획의 입력은 `00-brief.md`부터 관련 concept/systems/progression 문서, 출처·정본 데이터와 제공된 테스트 증거다. 출력은 프로젝트 기획 경로의 `05-validation.md`이며 문서 검수·검증 계획·실제 관찰·미실행을 구분한다.
- 원문 수정은 소유 단계로 전달한다. 전체 실행에서는 소유자가 현재 작성 권한 안에서 실제 파일을 수정하고 총괄이 수정·재검토 결과를 회수한다. 단독 검수에서 수정 권한이 없으면 구체적인 문제·근거·수정 위치·적용 전 상태를 전달한다. 검수 자체가 게임 제작·실행 권한을 추가하지 않는다.

## 용어 선택과 의미 대조

원작·신작·단독 검수 모두 [V3 집필 후 의미 검수](../game-planning-workflow/references/domain-dictionary.md#집필-후-의미-검수와-인계)를 적용한다. 사전 메타데이터와 기존 선택 기록부터 확인하고 실제 사용한 node ID/key의 정의·구별·의미 차이·예문·ref를 문장과 대조한다. 이름 정의/전문어 혼동, 기능의 하위 장르화, 부모·공용·다른 장르의 암묵 혼입, 예문의 작품 규칙 단정, 새 프로젝트 정의와 V3 정의의 혼동을 확인한다. 선택 기록이 없으면 사용된 용어부터 필요한 범위만 재구성하고 미확인을 밝힌다. 문제·본문 위치·근거·수정 소유자·실제 수정·재확인을 기존 검수 기록으로 연결한다.

## 원작 보고서 내용과 근거 검수

1. [내용 검토와 수정](../game-planning-workflow/references/deep-interview.md)으로 주된 내용의 누락·모순·불명확한 설명을 확인한다. 확인 가능한 근거로 질문에 답하고 소유 단계의 실제 수정과 영향받는 파일의 재검토를 연결한다.
2. [정형 목차](../game-planning-workflow/references/artifact-contract.md#원작-보고서의-정형-목차)와 [콘텐츠 상세 양식](../game-planning-workflow/references/artifact-contract.md#콘텐츠-상세-양식)을 대조한다. 게임 개요·전체 흐름·종류와 목표·확인된 진행 관계가 상세 사례보다 먼저 설명되는지, 아웃게임/인게임 분류와 제목 깊이가 실제 대상에 맞는지 확인한다.
3. 요청 범위·보고서 절·자료·실제 분석 범위를 연결한다. 해당 게임에 없는 항목의 제외 이유는 작업 기록에서 확인하고 의미 없는 빈 장은 제거한다. 장비의 획득·가격·장착과 플레이 중 사용, 장기 목표와 현장 완료 조건이 중복되거나 뒤섞였는지 확인한다.
4. 각 규칙·사례·핵심 설계 특징을 직접 원자료와 대조한다. [관찰과 해석의 경계](../game-planning-research/SKILL.md#관찰과-해석의-경계)에 따라 자료 설명·화면 관찰·규칙 추론·미확인을 구별하고 미확인 HP·스토리·히든 조건·정밀 시간을 만들어 넣은 내용을 수정한다.
5. 실제 동작과 UI 설명은 [실제 플레이 장면과 UI 취득](../game-planning-research/SKILL.md#실제-플레이-장면과-ui-취득)의 원자료·관찰 기록과 대조한다. 캡처가 첨부된 항목은 시각·설명·직접 원영상이 같은 장면인지 확인한다. 캡처가 없는 항목은 해당 절차의 문서 수준 설명 기준에 따라 근거 종류·캡처 유무·미확인이 드러나는지 확인한다. 이미지가 없다는 이유만으로 내용이나 중요한 조사 질문을 삭제하지 않는다.
6. 사실이나 화면이 부족하면 관련 절·조사 질문·필요한 장면·조건을 [game-planning-research](../game-planning-research/SKILL.md)에 전달한다. 조사 실패·차단·미지원과 내부 저장만 된 이미지는 확인·본문 배치 완료로 처리하지 않는다.
7. 내용과 근거의 수정 결과를 정본 작성자에게 회수한다. HTML이 요청됐거나 기존 HTML의 표시 검수가 필요하면 [front-game-planning-html](../front-game-planning-html/SKILL.md)에 최신 문서·출처·장면 묶음·문서로 유지한 항목의 근거 상태·미확인을 전달한다. 문서→표시 데이터→HTML의 일치, 실제 Mermaid·이미지 표시와 정상/좁은 화면·오프라인 확인은 그 스킬의 Chrome 검수 절차로 수행한다.

검수 결과에는 실제로 대조한 파일·자료·시각·화면 범위를 기록한다. 문자열이나 링크 검사 결과를 실제 웹 관찰·캡처 취득·브라우저 표시 검수로 바꾸지 않는다. 원작 분석의 완료 자료는 보고서 내용과 근거이며 신작 설계·제작·QA·사람 시험 계획을 자동 생성하지 않는다.

## 신작 기획 문서 검수

- 브리프의 원문 요구를 분위기·손맛·판타지까지 보존해 `원문 요구 | 반영 위치 또는 제외 결정과 이유 | 미해결 충돌`로 대조한다. 사용자 제약·MVP 범위와 관련 `C/SYS/P/V-*`가 일치하는지 확인한다.
- 레퍼런스의 채택·제외·변경 이유가 조사 `R-*`와 결정 `D-*`에 연결되는지, 안정적인 ID·근거·예정 참조와 실제 참조가 구별되는지 확인한다.
- 상태 전이, 성공·실패·재시작 조건, 자원·해금·금지 조합의 충돌을 확인한다. 같은 숫자의 단위·분모·적용 범위·정본·모델 버전을 대조하며 목표·가정·계산값·관측값과 미정·미측정·실제 0을 구별한다.
- 발견마다 구체적인 모순·영향·수정 소유 단계·관련 ID를 적고 [내용 검토와 수정](../game-planning-workflow/references/deep-interview.md)으로 실제 수정과 재검토를 연결한다. 관련 출처가 달라졌을 때 필요한 자료를 조사 단계에 전달한다.

## 신작 가설별 검증 계획

구현 전에는 가설별 질문과 실행 계획을 작성하고 필요한 디자인·구현 범위·준비 조건을 인계한다. 실제 실행 증거가 들어오면 같은 `V-*`의 계획·조건·원자료를 대조해 판정하고 다음 수정에 연결한다. 문서나 HTML의 완료는 플레이 가능한 경험의 준비와 사람의 재미 검증을 대신하지 않는다.

- 위험이 크거나 핵심 재미를 좌우하는 `C/SYS/P-*`부터 안정적인 `V-*` ID를 붙인다.
- 각 항목에 검증 질문, 대상 가설, 방법, 판정 기준, 필요한 증거, 상태, 후속 조치를 기록한다.
- 성공 기준은 관찰 가능한 행동이나 응답으로 정의한다. 가능한 경우 테스트 전에 기준을 정한다.
- 인원·시간·성공률의 고정 기본값을 두지 않는다. 대상 플레이어, 방법과 결과의 불확실성에 맞춰 선정 근거와 기준의 이유를 적는다.
- 방법은 문서 시나리오 검토, 수치 계산, 종이 테스트, 기존 프로토타입 플레이 등 질문에 답할 최소 수단을 고른다.
- 각 `V-*`에 테스트할 경험과 연결된 정본 `SYS/P-*`, 필요한 최소 행동·입력·피드백·콘텐츠, 빌드 준비 조건과 디자인·구현 인계를 적는다. 질문에 필요하지 않은 자산이나 전체 게임 제작을 범위에 넣지 않는다.
- 재미·손맛 등 플레이로 답할 질문은 해당 경험을 플레이 가능한 수준으로 준비한 뒤 실행한다. 준비되지 않았거나 실행 증거가 없으면 `not_run`으로 남긴다.
- 기능 프로토타입이나 자산 제작은 필요하고 사용자 범위에 포함될 때만 수행한다. 검증 스킬 호출 자체가 게임 디자인 자산 제작·런타임 구현을 허가하지 않는다.
- 사람이 테스트를 운영할 계획을 작성하거나 사람 플레이 증거를 분석할 때 [플레이테스트 운영 양식](references/playtest-session.md)을 읽고 필요한 내용을 해당 `V-*`에 붙인다. 별도 검증 정본을 만들지 않는다.
- 자료로 답할 질문, 조건부 설계 제안, 실제 플레이를 관찰해야 답할 질문을 구분한다. 시험의 준비 상태와 실제 실행 상태를 구별해 전달한다.

## 명시적으로 요청한 원작 플레이 시험

원작의 미확인 규칙이나 사람의 경험을 실제로 시험하라는 요청이 있으면 해당 질문·게임 조건·필요한 자료·실행 권한에 맞춰 별도 시험을 다룬다. 신작 `SYS/P-*`를 만들어 원작의 규칙 정본을 대체하지 않는다. 사람이 운영하는 시험은 [플레이테스트 운영 양식](references/playtest-session.md)을 해당 조사 질문이나 보고서 절에 연결한다. 공개 영상 분석은 조사 자료이며 운영한 사람 시험으로 기록하지 않는다.

## 실제 증거 다루기

- 검증 방법(문서 검토 / 수치 모델 / 직접 플레이 / 공개 플레이 영상 분석 / 사람 플레이 증거 분석), 플레이 주체(`human`/`agent`, 플레이에 해당할 때), 조건, 원자료, 판정 가능한 주장 범위를 근거 분류와 별도로 기록한다. 에이전트 문서 검토나 모델 계산을 사람 플레이로 적지 않는다.
- 테스트한 빌드·문서·모델 버전, 조건·기기·진행 구간·시각과 증거 위치를 남긴다.
- 관찰한 행동, 참여자 발언, 해석, 후속 제안을 구분한다. 없는 사람의 반응이나 측정치를 생성하지 않는다.
- 가상의 시연은 `illustrative`, 수치 모델은 `calculated`, 실제 관찰 기록은 `observed`, 미실행은 `not_run`으로 표시한다.
- `observed`는 성공 판정과 다르다. 성공 기준 충족 여부와 근거의 적용 범위를 별도로 적는다.
- 에이전트의 실제 플레이도 `observed`일 수 있지만 인간 경험·재미의 판정을 대신하지 않는다. 모델의 `calculated` 결과는 기록한 입력·행동 가정·시나리오 범위에서만 판단한다.
- 사람의 플레이·반응 근거 없이 재미 검증을 주장하지 않는다. 사람 자료가 있어도 대상·조건·사전 기준·원자료의 충분성을 확인하고 제한된 표본을 전체 사용자로 확대하지 않는다.

## 결과와 인계

- 원작은 내용·자료·장면 대응의 검수 결과와 중요한 미확인, 신작은 문서 검수·요청 범위의 계획·실제 관찰·미실행을 구별해 기록한다. 실행 근거가 없는 항목은 통과로 처리하지 않는다.
- 결과에 따른 수정·추가 조사의 소유 단계와 위치를 전달한다. 산출물 경로 / 실제 반영 위치 / 남은 충돌·미확인 / 수행한 대조와 미실행 범위 / 다음 단계 입력을 반환한다.
- 신작 구현 요청이 있으면 [구현 요청 시 인계](../game-planning-workflow/references/artifact-contract.md#구현-요청-시-인계)에 따라 정본 `SYS/P-*`와 `V-*`의 정상·경계·실패 사례 및 수락 조건을 현재 구현 워크플로에 전달한다. 사람의 경험 검증이 필요한 `V-*`는 별도로 유지한다.
- HTML 단계에는 모드·최신 문서·사전·직접 출처·목차·장면 묶음·중요한 미확인과 작업 기록 경계를 인계한다. [완료 인계](../game-planning-workflow/references/artifact-contract.md#완료-인계)에 따라 원작 독자용 보고서에는 게임 내용·근거를, 신작 기획에는 요청한 검증 상태·근거를 전달한다. 수행하지 않은 화면 검수·시험·승인·구현을 완료로 표현하지 않는다.
