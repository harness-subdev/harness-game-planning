# 게임 기획 검수와 검증

문서가 모순 없이 설명되는지, 가설을 어떻게 시험할지, 실제로 무엇이 관찰됐는지를 분리한다. 문서를 완성했다는 이유로 게임의 재미가 검증됐다고 말하지 않는다.

## 시작과 소유권

- 먼저 [공통 산출물 계약](../game-planning-workflow/references/artifact-contract.md)을 읽는다.
- `00-brief.md`부터 `04-progression.md`, `sources.json`, 관련 정본 데이터와 제공된 테스트 증거를 읽는다.
- 출력은 프로젝트 기획 경로의 `05-validation.md`다. 실제 생성한 증거만 필요에 따라 `evidence/`에 보관한다.
- 원본 수정은 해당 소유 단계로 인계한다. 다른 단계 문서와 `workflow.json`은 수정하지 않는다.
- 선행 산출물이 없으면 검수 가능한 범위와 제외된 범위를 밝힌다. 검수 범위를 채우기 위해 내용을 지어내지 않는다.
- 테스트 참여자·빌드·실행 권한이 없어도 문서 검수와 실행 가능한 검증 계획을 작성한다.

## 두 사용 시점과 세 가지 결과

- **구현 전:** 문서 일관성을 검수하고 가설별 테스트를 설계한다. 테스트할 경험에 필요한 최소 디자인·구현 범위와 준비 조건을 인계한다.
- **실제 실행 증거가 들어온 뒤:** 같은 `V-*`의 계획·조건·원자료를 대조해 가설을 판정하고 다음 수정으로 연결한다. 조건이나 기준을 바꾸면 변경 이유를 남긴다.

실제 제작 반복은 기획 → 검증 질문·계획 → 필요한 디자인·구현 → 플레이테스트 → 기획·디자인·구현 수정이다. 문서 단계 완료나 HTML 제작은 플레이 가능한 경험의 준비와 재미 검증을 대신하지 않는다.

1. **문서 일관성:** 용어·조건·참조·수치·범위가 서로 맞는지 검사한 결과를 기록한다.
2. **검증 계획:** 아직 수행하지 않은 플레이 테스트의 질문과 실행 방법을 기록한다.
3. **실제 측정:** 실제 테스트 조건과 원자료가 확인된 결과만 관찰 근거로 기록한다.

## 문서 일관성 검수

- 브리프의 원문 요구를 분위기·손맛·판타지까지 보존해 `원문 요구 | 반영 C/SYS/P/V 위치 또는 제외 D와 이유 | 미해결 충돌`로 대조한다. 핵심 경험·루프·시스템·진행이 사용자 제약과 MVP 범위에 연결되는지 확인한다.
- 레퍼런스의 채택·제외·변경 이유가 조사 `R-*`와 결정 `D-*`에 연결되는지 대조한다. 보이는 동작과 내부 규칙 추정을 섞어 누락이나 충돌을 해소하지 않는다.
- 안정적인 ID의 중복·누락·끊어진 참조와 출처→관찰→결정→명세의 연결을 확인한다.
- 상태 전이, 성공·실패·재시작 조건, 자원·해금·금지 조합의 충돌을 확인한다.
- 같은 숫자의 단위·분모·적용 범위·정본·모델 버전을 대조한다. 서로 다른 버전의 값을 평균내어 충돌을 숨기지 않는다.
- 목표·가정·계산값·관측값, 미정·미측정·실제 0이 뒤섞였는지 확인한다.
- 관련 출처 버전과 현재 기획의 차이를 확인하되 모든 조사를 기계적으로 재실행하지 않는다.
- 발견마다 영향받는 ID, 구체적인 모순, 결과에 미치는 영향, 수정 소유 단계와 우선순위를 적는다.

## 가설별 검증 계획

- 위험이 크거나 핵심 재미를 좌우하는 `C/SYS/P-*`부터 안정적인 `V-*` ID를 붙인다.
- 각 항목에 검증 질문, 대상 가설, 방법, 판정 기준, 필요한 증거, 상태, 후속 조치를 기록한다.
- 성공 기준은 관찰 가능한 행동이나 응답으로 정의한다. 가능한 경우 테스트 전에 기준을 정한다.
- 인원·시간·성공률의 고정 기본값을 두지 않는다. 대상 플레이어, 방법과 결과의 불확실성에 맞춰 선정 근거와 기준의 이유를 적는다.
- 방법은 문서 시나리오 검토, 수치 계산, 종이 테스트, 기존 프로토타입 플레이 등 질문에 답할 최소 수단을 고른다.
- 각 `V-*`에 테스트할 경험과 연결된 정본 `SYS/P-*`, 필요한 최소 행동·입력·피드백·콘텐츠, 빌드 준비 조건과 디자인·구현 인계를 적는다. 질문에 필요하지 않은 자산이나 전체 게임 제작을 범위에 넣지 않는다.
- 재미·손맛 등 플레이로 답할 질문은 해당 경험을 플레이 가능한 수준으로 준비한 뒤 실행한다. 준비되지 않았거나 실행 증거가 없으면 `not_run`으로 남긴다.
- 기능 프로토타입이나 자산 제작은 필요하고 사용자 범위에 포함될 때만 수행한다. 검증 스킬 호출 자체가 게임 디자인 자산 제작·런타임 구현을 허가하지 않는다.
- 사람이 테스트를 운영할 계획을 작성하거나 사람 플레이 증거를 분석할 때 [플레이테스트 운영 양식](references/playtest-session.md)을 읽고 필요한 내용을 해당 `V-*`에 붙인다. 별도 검증 정본을 만들지 않는다.
- 사용자 결정이 필요한 질문과 실제 플레이를 관찰해야 답할 질문을 구분한다.

## 실제 증거 다루기

- 검증 방법(문서 검토 / 수치 모델 / 직접 플레이 / 사람 플레이 증거 분석), 플레이 주체(`human`/`agent`, 플레이에 해당할 때), 조건, 원자료, 판정 가능한 주장 범위를 근거 분류와 별도로 기록한다. 에이전트 문서 검토나 모델 계산을 사람 플레이로 적지 않는다.
- 테스트한 빌드·문서·모델 버전, 조건·기기·진행 구간·시각과 증거 위치를 남긴다.
- 관찰한 행동, 참여자 발언, 해석, 후속 제안을 구분한다. 없는 사람의 반응이나 측정치를 생성하지 않는다.
- 가상의 시연은 `illustrative`, 수치 모델은 `calculated`, 실제 관찰 기록은 `observed`, 미실행은 `not_run`으로 표시한다.
- `observed`는 성공 판정과 다르다. 성공 기준 충족 여부와 근거의 적용 범위를 별도로 적는다.
- 에이전트의 실제 플레이도 `observed`일 수 있지만 인간 경험·재미의 판정을 대신하지 않는다. 모델의 `calculated` 결과는 기록한 입력·행동 가정·시나리오 범위에서만 판단한다.
- 사람의 플레이·반응 근거 없이 재미 검증을 주장하지 않는다. 사람 자료가 있어도 대상·조건·사전 기준·원자료의 충분성을 확인하고 제한된 표본을 전체 사용자로 확대하지 않는다.
- UI 확인은 연결된 Chrome의 지원 API를 사용한다. Playwright를 사용하지 않는다.

## 결과와 인계

- `05-validation.md`에서 문서 검수 결과, 검증 계획, 실제 관찰, 미실행·보류 항목을 구분해 읽을 수 있게 한다.
- 결과에 따른 유지·수정·추가 확인 제안과 해당 소유 단계·항목 ID를 기록한다.
- 구현 요청이 있으면 [공통 계약의 구현 요청 시 인계](../game-planning-workflow/references/artifact-contract.md#구현-요청-시-인계)에 따라 정본 `SYS/P-*`와 `V-*`의 정상·경계·실패 사례 및 수락 조건을 현재 구현 워크플로에 전달한다. 사람 경험 검증이 필요한 `V-*`는 별도로 유지한다.
- 실행 증거가 없는 항목이 통과 처리되지 않았는지, 증거 위치가 실제 존재하는지 확인한다.
- 산출물 경로 / 반영한 결정 ID / 남은 가정·충돌 / 검수 결과 / 다음 단계 입력을 반환한다.
- HTML 단계에는 표시할 검증 상태와 근거를 전달한다. 문서 단계 완료를 실측·승인·구현 완료로 바꾸지 않는다.
