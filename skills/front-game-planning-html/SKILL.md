# 게임 기획 HTML 열람본

요청한 게임 문서를 읽기 좋은 로컬 HTML로 만든다. 원작 레퍼런스 보고서는 게임 설명과 실제 근거를 보여 주는 열람본으로, 신작 기획 문서는 결정·구현·검증 상태를 함께 읽는 기획서 허브로 제작한다. 단독 호출도 가능하며 없는 선행 문서를 자동으로 만들지 않는다.

## 입력과 담당 범위

1. [공통 계약의 문서 모드](../game-planning-workflow/references/artifact-contract.md#문서-모드와-원작-레퍼런스-보고서)를 읽고 요청한 산출물과 원본 경로를 확인한다. 사용자가 지정한 경로를 우선하며, 새 기획 폴더가 필요할 때의 기본 경로는 프로젝트의 `game-planning/`이다. 제공된 사용자 피드백 정본은 요약 대신 전체 읽고 적용한다.
2. 원작 분석은 지정된 보고서 또는 `01-research.md`와 그 보고서에 사용한 출처·로컬 캡처·그림을 읽는다. 자료·장면 취득 기록과 문서 검수 기록은 대조 입력이다. 신작 단계 문서나 제작·시험 계획을 원작 보고서의 빈칸으로 채우지 않는다.
3. 신작 기획은 요청 범위에 존재하는 `00-brief.md`, `01-research.md`, `02-concept.md`, `03-systems.md`, `04-progression.md`, `05-validation.md` 등을 읽는다. 해당 프로젝트의 `sources.json`, `workflow.json`, 사전이 있으면 함께 대조한다. 없는 입력과 오래된 입력은 작업 기록에 남기고 허브에서 실제 초안·미실행 범위를 표시한다.
4. 명칭은 [용어 정본과 명칭 대조](../game-planning-workflow/references/game-terminology.md#용어-정본과-명칭-대조)를 따른다. 원문 소유 단계가 정한 정의·원어·명칭 상태를 투영한다. 새 사전 작성이나 게임 내용 변경이 필요하면 담당 단계로 돌려보낸다.

원본 문서가 내용의 정본이고, `portal.json` 등의 표시 데이터와 HTML은 파생 출력이다. 내용 오류는 원문 소유 단계에서 고친 뒤 다시 투영한다. 표시 오류는 HTML 단계에서 고친다. HTML만 요청한 호출에 새 내용 인터뷰를 강제하지 않는다. 이 스킬은 게임 화면·아트·입력·시뮬레이터를 제작하지 않으며, 열람본 제작으로 게임의 재미나 내부 구현을 검증했다고 보고하지 않는다.

## 렌더러 선택

선택하기 전에 기존 프로젝트 렌더러의 실제 입력 형식과 출력을 읽는다. 아래 요구를 실제로 표시하는 렌더러를 재사용한다.

| 산출물 | 필요한 표시 | 선택 |
| --- | --- | --- |
| 원작 레퍼런스 보고서 | [정형 목차](../game-planning-workflow/references/artifact-contract.md#원작-보고서의-정형-목차)의 절 깊이, [콘텐츠 상세](../game-planning-workflow/references/artifact-contract.md#콘텐츠-상세-양식), 확보한 실제 캡처와 인접 설명·시각·직접 출처, 캡처 없는 항목의 문서 수준 설명·근거 상태, Mermaid 그림, 독자용 본문 | 지원하는 기존 프로젝트 렌더러를 사용한다. 빠진 기능은 보고서 HTML 제작 요청의 범위에서 그 프로젝트의 표시 생성기를 최소 보완하고 다시 생성·검수한다. |
| 신작 기획 허브 | 요청한 문서의 내용과 `SYS/P/V-*`, 수락 조건, 결정·구현·근거 상태 | 기존 프로젝트 렌더러를 우선한다. 텍스트·표·한 단계 상세 항목·상태·문서 목록만으로 요청을 충족할 때는 제공 version 1을 사용할 수 있다. |

version 1의 실제 지원과 한계는 [입력 형식](references/portal-format.md#지원-범위와-렌더러-선택)에 있다. 미지원 필드를 추가하거나 `status`를 생략해도 원작 보고서 렌더러가 되지 않는다. 필요한 캡처·그림을 링크나 파일명으로 바꾸거나 목차를 평탄화해 이 형식에 맞추지 않는다. 하네스 문서 점검 요청만으로 프로젝트 렌더러 변경을 실행하지 않는다.

## 제작과 인계 순서

필요한 단계만 실행하되, 각 단계의 결과를 다음 담당에게 넘긴다.

| 단계 | 담당 기존 스킬 | 입력·작업 | 출력·다음 단계 |
| --- | --- | --- | --- |
| 1. 내용과 근거 확인 | `front-game-planning-html` | 원본 문서·피드백·출처·취득 기록을 읽고 표시할 범위를 확인한다. | 누락·내용 오류는 2단계, 확인된 문서는 3단계로 넘긴다. |
| 2. 빠진 조사와 원문 보완 | [game-planning-research](../game-planning-research/SKILL.md); 신작의 해당 내용은 [game-planning-concept](../game-planning-concept/SKILL.md), [game-planning-systems](../game-planning-systems/SKILL.md), [game-planning-progression](../game-planning-progression/SKILL.md) | 조사 질문과 필요한 실제 화면을 연구 단계에 넘긴다. [실제 플레이 장면과 UI 취득](../game-planning-research/SKILL.md#실제-플레이-장면과-ui-취득)에 따라 조사하고 원문 소유 단계가 확보한 근거로 본문을 갱신한다. | 최신 본문·확보한 캡처·장면 설명·직접 출처·근거 상태를 HTML 단계로 반환한다. 캡처가 없는 항목도 연구 단계의 문서 수준 설명으로 인계하며, 취득 실패는 성공 결과로 넘기지 않는다. |
| 3. 흐름과 진행 그림 준비 | [mermaid-diagrams](../mermaid-diagrams/SKILL.md) | 원문에서 확인한 반복·분류·진행 관계와 그림의 범위를 넘긴다. 실제 게임의 관계를 추가로 가정하지 않는다. | Mermaid 원문·짧은 설명·오프라인에 읽을 그림을 4단계로 넘긴다. 기존에 준비된 그림이 있으면 대조해 재사용한다. |
| 4. 표시 데이터 작성 | `front-game-planning-html` | 선택한 렌더러의 형식으로 원본을 투영한다. 제목·절 순서·깊이·표 행·그림·이미지 묶음·원자료 링크를 대응시킨다. | 표시 데이터와 원문 대응을 작업 기록에 남기고 5단계로 넘긴다. |
| 5. HTML 생성 | `front-game-planning-html` | 기존 생성·검사 명령을 실행한다. 필요한 프로젝트 표시 기능 보완도 이 단계에서 수행한다. | HTML·로컬 이미지·그림과 생성 결과를 6단계로 넘긴다. |
| 6. 문서와 출력 대조 | [game-planning-validation](../game-planning-validation/SKILL.md) | 원본 → 표시 데이터 → HTML을 대조한다. 영상 시각이 있는 문장·표 행·캡션을 원문 근거와 대조하고, 첨부된 캡처의 대응 또는 문서 수준 설명의 근거 상태를 확인한다. | 누락·불일치는 내용 또는 표시 담당 단계로 반환한다. 대조한 출력과 남은 한계를 7단계로 넘긴다. |
| 7. 실제 화면 확인 | `front-game-planning-html`; 필요하면 [webapp-testing](../webapp-testing/SKILL.md) | 연결된 Chrome의 정확한 작업 탭에서 정상·좁은 화면, 로컬 읽기, 지원하는 상호작용을 확인한다. | 실제 확인한 범위·실패·미지원과 출력 경로를 총괄에 인계한다. |

4단계에서는 원작의 [독자용 문체와 작업 기록의 경계](../game-planning-workflow/references/game-terminology.md#독자용-문체와-작업-기록의-경계)를 모든 표시 위치에 적용한다. 신작의 상태·수락 조건은 원문의 의미를 유지하며, version 1에서 여러 상태 축이 필요하면 [상태와 검증 문맥의 투영](references/portal-format.md#상태와-검증-문맥의-투영)대로 기존 문단·표에 넣는다.

5단계에서 version 1을 선택한 신작 기획 허브는 이 스킬 경로를 기준으로 다음 명령을 실행한다. 다른 렌더러에는 해당 프로젝트의 실제 명령을 사용한다.

```sh
python3 scripts/build_portal.py /absolute/project/game-planning/portal.json /absolute/project/game-planning/index.html
python3 scripts/self_check.py
```

제공 빌더의 자체 점검은 합성 입력의 형식·렌더링·CLI 출력 보존을 검사한다. 원문의 반영, 출처 사실성, 최신성, 실제 브라우저 표시나 사람의 경험은 확인하지 않는다.

## 실제 표시 확인

Chrome 연결을 먼저 발견하고 전용 작업 탭의 ID·URL을 확인한다. 그 탭의 지원되는 접근성·입력·스크린샷 API로 다음을 확인한다. `webapp-testing`을 사용해도 Playwright는 사용하지 않는다.

- 제목과 목차의 순서·깊이·링크 대상, 상세 펼침·검색이 있는 경우 그 동작을 확인한다.
- 정상·좁은 화면에서 표의 마지막 열까지 읽고 글자, 열 너비, 줄바꿈, 여백, 목록 들여쓰기를 확인한다. 정렬 CSS가 있다는 것만으로 줄맞춤 검수가 끝나지 않는다.
- Mermaid가 코드 대신 실제 그림으로 보이는지, 글자·연결선·범위 설명이 읽히는지 확인한다.
- 첨부된 사진은 최종 저장 픽셀과 표시된 대상·캡션·영상 시각·직접 원영상 링크를 대조하고 전후 비교에 쓰는 장면이 설명과 대응하는지 확인한다. 캡처가 없는 항목은 연구 단계에서 정리한 문서 수준 설명·근거 상태·중요 미확인이 HTML에도 유지되는지 확인한다. 불일치하는 이미지는 사용하지 않고 해당 설명의 근거를 원문에서 바로잡아 다시 투영한다.
- `file://` 또는 로컬 HTTP에서 로컬 이미지와 설명을 읽는다. 기본 문서와 그림은 외부 폰트·CDN·이미지·API 요청에 의존하지 않게 한다. 오프라인·영상 로딩 실패에도 문서 설명·근거 상태·직접 출처 링크와 확보한 로컬 캡처가 남아야 한다. 요청된 인쇄본은 화면 밖 이미지나 표의 누락도 확인한다.

네이티브 창 캡처 실패를 탭 접근 실패로 단정하지 않는다. 전용 탭의 접근성 상태·지원 입력·스크린샷을 확인한 뒤 불가능한 기능만 작업 기록에 남긴다. 문자열·상대 링크 검사나 자체 점검 통과를 실제 화면 검수 완료로 보고하지 않는다.

## 영상 표시와 완료

장면 취득과 관찰·해석의 기준은 [연구 단계](../game-planning-research/SKILL.md#관찰과-해석의-경계)의 정본을 따른다. HTML에는 확보한 캡처와 설명·시각·직접 원영상 링크를 가까이 배치하고, 캡처가 없는 항목은 연구 단계의 문서 수준 설명과 근거 상태를 그대로 표시한다. 임베드는 요청되었거나 필요한 경우에 지원되는 프로젝트 렌더러로 제공하며 온라인 필요·제한과 직접 원영상 링크를 표시한다. 추가한 임베드는 Chrome에서 구간 링크·재생 또는 제한 표시·좁은 화면을 확인한다. 전체 영상 다운로드·재업로드를 자동 의무로 만들지 않는다.

[완료 인계](../game-planning-workflow/references/artifact-contract.md#완료-인계)에 따라 원본 해시, 실제 표시 데이터·HTML·로컬 자산, 대조 결과, 브라우저에서 확인한 범위와 남은 한계를 총괄에 전달한다. 원본 변경으로 오래된 열람본은 재생성과 필요한 대조 후에만 최신으로 바뀐다. 최종 작업 보고에는 출력 절대 경로와 수행 범위·검증 결과·제약을 적는다. 내부 작업 기록은 원작 독자용 HTML에 넣지 않는다. 일상적인 생성·갱신에 별도 승인 단계를 추가하지 않으며 배포·공유는 요청된 범위에서만 진행한다.
